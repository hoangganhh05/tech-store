# US-15.3 — Production deployment

The production deployment runs the Docker Compose stack from US-15.1 behind
Caddy. Caddy owns ports 80 and 443, redirects HTTP to HTTPS, obtains and
renews the TLS certificate for `APP_DOMAIN`, and proxies only to the private
frontend container. The frontend continues to proxy `/api/` internally to the
Backend.

## Prerequisites

- A Linux VPS/hosting machine with a public IPv4 address.
- A DNS `A`/`AAAA` record for `APP_DOMAIN` pointing to that server before the
  first deployment, so the ACME certificate authority can validate the domain.
- Docker Engine, Docker Compose plugin, Git and Curl installed.
- Inbound firewall rules for TCP 80 and 443 only. Do not expose MySQL or the
  Backend port publicly.

## First deployment

```bash
git clone https://github.com/hoangganhh05/tech-store.git
cd tech-store
git switch main
cp .env.example .env
# Edit .env with real domain, passwords, JWT key and SMTP credentials.
bash ./scripts/preflight-production-server.sh
bash ./scripts/deploy-production.sh
```

Generate a dedicated `JWT_SECRET` with
`./scripts/new-production-jwt-secret.ps1` on Windows before adding it to the
server's private `.env`. Never copy the development secret or commit `.env`.

## Redeploy

On the server, run the same command after a new version is merged into `main`:

```bash
cd /path/to/tech-store
bash ./scripts/deploy-production.sh
```

The script refuses a dirty server checkout, fast-forwards only to `origin/main`,
rebuilds containers, waits for health checks, then verifies HTTPS storefront and
the public API health endpoint.

## Production acceptance checklist

1. `https://APP_DOMAIN` opens the storefront without a certificate warning.
2. `https://APP_DOMAIN/api/v1/health` returns HTTP 200.
3. HTTP redirects to HTTPS; port 8080, Backend port 8080 and MySQL port 3306
   are not publicly reachable.
4. Check customer browse/cart/checkout and an admin login/order update with
   controlled production credentials.
5. Run `bash ./scripts/verify-production.sh https://APP_DOMAIN` after each deploy.

The repository contains no server address, domain or credentials, so the final
external deployment and live acceptance require the hosting details from the
project owner.
